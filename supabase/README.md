# The database side

Two things live here, both about the same problem: a bug report that reaches the
table and nobody's attention.

- `functions/feedback-email/` — turns a row in `public.feedback` into an email.
- `migrations/20260905_feedback_email.sql` — the trigger that calls it (and
  `20261022_report_screenshots.sql`, below, which gives it longer and adds the
  screenshots' bucket).

Both are deployed. The one thing they need that a repository must never hold is
an API key, so until the four settings below are filled in, the trigger runs,
logs that it has nothing to send with, and lets the report through untouched.
Nothing breaks in the meantime; the reports simply keep arriving silently, the
way they did before.

## Finishing the wiring

**1. Get a Resend key.** [resend.com](https://resend.com) → sign up (GitHub works)
→ **API Keys** → **Create API Key** → copy it. The free tier is 3,000 emails a
month, which is several orders of magnitude more than this will ever send.

**2. Put it in Supabase.** Supabase dashboard → the `fractal-ai-builder` project
(that is the SUPABASE project's name, which did not change when the GitHub
repository was renamed to `fractal-remote` — renaming one does not rename the
other, and the dashboard still lists it under the old one)
→ **Edge Functions** → **Secrets** → add:

| name | value | needed? |
|---|---|---|
| `RESEND_API_KEY` | the key from step 1 | yes |
| `FEEDBACK_TO` | where reports should land | only to change the default |
| `FEEDBACK_FROM` | who they come from | only to change the default (`noreply@newbold.cloud`) |

That is the whole of it. The next report sends an email.

There is deliberately nothing to keep in step by hand. The shared secret between
the trigger and the function is generated by the database and read back by the
function through an RPC only `service_role` may call, using the key Supabase
injects into every function on its own. An earlier version asked for a string to
be invented and typed into two places, which is the step that breaks — and it
breaks silently, as a 401 nobody is looking at.

### Sending from your own domain, and the catch that cost an evening

Both functions now send from `noreply@newbold.cloud` with nothing set, because
`newbold.cloud` is verified with Resend. Set `FEEDBACK_FROM` or `DOWNLOAD_FROM`
only to change that.

It used to be `onboarding@resend.dev`, Resend's shared sender, which works on
the day you sign up — and that is why it was written that way. **What nobody
wrote down is the limit: that address may only send to the ONE address that
owns the Resend account.** Every other recipient comes back 403, with this:

> You can only send testing emails to your own email address
> (justinnewbold@gmail.com). To send emails to other recipients, please verify
> a domain at resend.com/domains.

Which is invisible for a long time, because it is not obviously a limit. The
feedback email kept working for nine months — it only ever sends to that same
gmail. The DOWNLOAD LINK broke the moment it was tried, because a download link
goes to whoever typed their address into the phone.

`newbold.cloud` had been sitting in Resend at **failed** since December with
none of its three DNS records ever added. They are in the Vercel zone now:

| type | name | value |
|---|---|---|
| TXT | `resend._domainkey` | the DKIM key Resend issued |
| TXT | `send` | `v=spf1 include:amazonses.com ~all` |
| MX | `send` | `feedback-smtp.us-east-1.amazonses.com` (priority 10) |

**If mail ever stops again, check that domain first.** Resend → Domains. A
domain can fall back to `failed` if a record is edited or removed, and the
symptom at the phone is the same four words either way: *the mail service
refused it*.

## How it is put together, and why

**The app does not send the email.** It inserts a row and is finished. Someone
reporting a bug is already having a bad time, often on a stage, often on a phone
with two bars — the insert is the promise this app makes to them, and it is kept
whether or not any mail ever leaves. A trigger also cannot be bypassed: every
row gets its notification, including ones written by hand in the dashboard.

**`pg_net` is asynchronous.** `net.http_post` queues the request and returns, so
the INSERT never waits on Resend, on the function, or on the internet.

**The function authenticates itself.** `verify_jwt` is off, because the caller is
Postgres rather than a signed-in person. Anyone who has the app has the anon key,
so a JWT check would not have distinguished the database from a stranger anyway —
the `x-hook-secret` header does. Without it the function's URL would be a button
anybody could press to put whatever they liked in an inbox.

**Failures are logged, not raised.** A missing key, a refusal from Resend, a
malformed row — all of them answer 200 and write a line to the function log. The
row is already saved and the person has already been thanked; a non-2xx would
only record a failure in `net._http_response` that nobody is watching. When mail
stops arriving, the function log is the place to look.

## Checking it

```sql
-- the plumbing
select
  (select count(*) from pg_trigger where tgname = 'feedback_email' and not tgisinternal) as trigger_installed,
  (select count(*) from pg_extension where extname = 'pg_net') as pg_net_installed,
  (select count(*) from vault.decrypted_secrets where name = 'feedback_hook_secret') as hook_secret_set;

-- what the last few calls actually did
select id, status_code, created
from net._http_response
order by created desc
limit 5;
```

`200` with `{"sent":true}` is a sent email. `200` with
`{"sent":false,"why":"not configured"}` means everything is wired and
`RESEND_API_KEY` is still missing. `401` means the function could not read the
hook secret — check that `feedback_hook_secret()` still grants execute to
`service_role`.

To exercise the whole chain without leaving a fake report in the table, call the
function the way the trigger does:

```sql
select net.http_post(
  url := 'https://biznwrqeckviawjuhvyg.supabase.co/functions/v1/feedback-email',
  headers := jsonb_build_object(
    'Content-Type', 'application/json',
    'x-hook-secret', (select decrypted_secret from vault.decrypted_secrets
                      where name = 'feedback_hook_secret' limit 1)
  ),
  body := jsonb_build_object(
    'id', '00000000-0000-0000-0000-000000000000',
    'kind', 'bug',
    'message', 'Wiring check.',
    'context', jsonb_build_object('version', 'test')
  )
);
```

Then read `net._http_response` as above. Note that a rolled-back transaction
sends nothing: `net.http_post` queues its request inside the caller's
transaction, so a test wrapped in `begin; ... rollback;` proves the INSERT
survives but never exercises the HTTP call.

## Reports: a note, screenshots, and the whole log in the email

"Is this all the information the logs send? Where's the space to enter a
message and upload photos? Let's get it all set up if it's not already."
(22 October 2026.) The email a report made had the kind, the message, the
context bullets and the row id, and none of the log. Three pieces now:

- `functions/feedback-email/` — the email carries the log's head (which
  build, unit, computers and which one is driven), the line saying which
  computer answered and why it is the one driven, the last lines that went
  wrong, the end of the run before, the top of the computer's own log, and
  the whole log attached as a `.txt`. Screenshots are read from the bucket
  with the service key and **attached**, shown in the body by `cid:` (a link
  that expires is dead by the time a report from a gig is read; one that
  does not is a public picture). Each is at most 1.5 MB from the app (2 MB
  in the bucket), so five (three until 7 November 2026, below) are about
  10 MB encoded, 13.3 MB at the bucket's 2 MB each, inside Resend's 40 MB and
  Gmail's 25 MB. A row may only name pictures under its own sender's folder.
  When nobody typed an address, the reply goes to the account's own email,
  read from the account service and labeled "(the account's email)". Every
  request it makes has a ten-second deadline, and a picture or address that
  cannot be had costs the email one line.
- `migrations/20261022_report_screenshots.sql` — the private bucket
  `report-shots` (JPEG only, 2 MB a file), one rule for putting a picture in
  (`<account id>/<key>-<1..3>.jpg`, `<1..5>` since
  `20261107_report_five_shots.sql`, or `anon/…` signed out, and only while
  `report_shots_room(folder)` says there is room: fewer than 15 in the last
  hour in that folder, an account's or anon/, anon/ under 100 MB, and the
  bucket under 200 MB, so a stranger signed out can never shut an account's
  pictures out), and nothing for reading, listing, replacing or removing.
  `report_shots_due()` lists what is to go: older than 7 days, or older than
  an hour and named by no report of its own (a row from the folder's own
  sender, among its first three; five since `20261107_report_five_shots.sql`,
  which makes the rule and this again). And `notify_feedback()` again,
  unchanged but for sixty seconds for the email instead of five. The row's
  shape does not change: the pictures' places ride in `context.screenshots`.
- `migrations/20261022_report_shots_sweep.sql` — once a day (pg_cron), asks
  the email function to delete what `report_shots_due()` lists. Needs pg_cron
  turned on; until it is, the same tidy happens whenever a report comes in.
  Applied only after the new feedback-email is deployed (step 3 below).
- `functions/delete-account/` — Delete account removes the account's
  screenshots through Storage's own API, before the rows that name them, and
  only its own (its folder, or anon/ named by a report sent signed out). Then
  it emails the developer the row ids of the reports that went, so their
  emails can be found and deleted too: the privacy page promises that. The
  note goes as soon as the rows have gone, even when the account's own
  delete is then refused (a try again finds no rows to list), and when the
  reports cannot be looked up, nothing is deleted and the person is asked to
  try again in a minute.

The email attaches a picture to one email only (a row naming a picture
another row named gets a line instead), only bytes that start as a JPEG
does, and goes again without its pictures if Resend refuses it with them.

**Deleting a report row by hand leaves its pictures in the bucket**, because
Storage keeps its files apart from the table and refuses a SQL delete on
`storage.objects`. Nothing has to be done: an hour after no row names them,
the next tidy deletes them. To have them gone at once, delete the paths the
row's `context.screenshots` names in the dashboard's Storage view (bucket
`report-shots`), before or after deleting the row.

## The setup emails (paid, but no computer yet)

"Get new buyers past 'no computer yet.' ... one friendly email a day after
buying if no computer has signed in, and a 'paid but stuck' list on your
Developer page." (15 October 2026.) Three pieces, none of them live until
Justin says so, and the emails themselves off even then:

- `migrations/20261015_setup_reminders.sql` — the dates kept from now on
  (when an account was first seen with the full version; when a computer app
  first signed in with it, kept for every account; when each setup email went
  or was refused; and when Justin left one out), the
  rule for who is due one, the switch (`setup_reminder_switch`, **off**), the
  list `owner_setup_stuck()` for the Developer page, and a hook secret made in
  vault like the feedback one. Everything is service_role only.
- `migrations/20261015_setup_reminders_schedule.sql` — pg_cron, and one job at
  23 minutes past every hour that calls `run_setup_reminders()`. A file of its
  own so that if pg_cron is refused, nothing else is.
- `functions/setup-reminder/` — reads the switch; off, it only counts; on, it
  claims each due email in the database and then sends it through Resend.
  The claim reads the switch again before every email, so turning the emails
  off in the middle of a run stops that run at the next one. Each email goes
  from `noreply@newbold.cloud`, with replies to `justinnewbold@gmail.com`.
  At most two emails per account, ever: the first two days after the full
  version is first seen, one reminder a week after that (since 1 November
  2026, 20261101_setup_timing.sql: it was a day and four days), none once a
  computer has signed in, none to an unconfirmed address, and none after the
  mail service refuses one of them.

  **A refusal stops the run**, and what happens to that one account depends on
  Resend's status and, for a 400 or 422, on what its answer was about. A bad
  address does not bounce at the moment of sending (Resend takes it and
  reports the bounce later), so most refusals are the service or our own
  request, not the person. Even most 400s and 422s are ours: Resend answers
  400 "API key is invalid" from every endpoint when the key is not in a key's
  shape, 400 for a field it cannot read (a mistyped `SETUP_FROM`), and 422 for
  a missing field. Only an answer about the `to` field is the person's. The
  function reads Resend's answer to sort it and keeps nothing of it but its
  error name (`validation_error` and the like), because the message can quote
  the address.

  | Resend answered | What it means | What happens |
  | --- | --- | --- |
  | 400, 422 about the `to` field | the mail service won't take this person's address | `failed_at` is written, and that account gets no more until Justin taps **Try the email again** on their sheet |
  | 400, 422 about anything else, or an answer that won't read | the request itself was turned down: the key in the wrong shape, `SETUP_FROM` or `SETUP_REPLY_TO` mistyped, a field missing | the claim is taken back (`release_setup_reminder`); the run tries the next email once, to tell the request from the person, and stops when that one is turned down too; the next hour tries again |
  | 401, 403 | the mail key was refused | the claim is taken back; the run stops; the next hour tries again |
  | 429 | a sending limit was reached | the same: taken back, tried next hour |
  | 5xx, no answer, or anything else | it may have gone: a fault, and a 502 or 504 from a gateway above all, can come back after Resend took the email | the claim stays, so it reads as sent and is never sent twice. After a first email the reminder still follows four days on; after a reminder, nothing |

  So a wrong or rotated `RESEND_API_KEY`, or a typo in `SETUP_FROM`, costs
  nobody anything: every hour one email (two, for a 400 or 422) is tried,
  turned away, handed back, and the log says what it was, for example
  `the mail key was refused (status 401)` or `the mail service turned the
  request itself down, not the address (check RESEND_API_KEY and SETUP_FROM)
  (status 400, validation_error)`, until it is fixed. A fault on Resend's side
  costs at most the one email it stopped at, never a second copy.

  **Try the email again** (grant-access `try-again`, then
  `clear_setup_reminder_refusal`) forgets the refusal, and the one email it
  stopped is due again by the usual rule. A refused email never went, and its
  date was emptied when the refusal was written, so this is never a second
  copy and never a third email.

  Every real email also carries an `Idempotency-Key`,
  `setup-reminder/<first|reminder>/<account id>` (never the address). Resend
  keeps it for 24 hours and answers a repeat of the same key and words without
  sending again, so an email handed back after a 401, 403, 429, or a 400 or
  422 about the request, and tried again inside that day cannot arrive twice,
  even if Resend had taken it. The
  samples carry none.

`functions/grant-access/` gains five actions behind the same lock: `stuck`
(the list), `reminders` (the switch), `leave-out`, `try-again` (a refused
email due again), and `reminder-sample` (both emails, marked [Sample], to the
reply address).

function runs. Deploy it again with the flag. There is no `config.toml` here
to remember it.

## How many people, day by day (counts only, naming nobody)

"A day-by-day history of how many people use the app, on your Developer
page" (approved 4 November 2026). Developer → Customers → People counts
who used the app from each account's latest sign-in, device check-in and
RevenueCat sighting, and each of those keeps only the latest time, so a day
can only be counted on that day. So the database asks for the day's count a
few minutes before each UTC midnight, and keeps the totals. People gains a
Day by day chart of the last 30 days, and a System versions list read from
what RevenueCat already keeps (no history needed for that one). Nothing new
is collected from anybody. Four pieces:

- `migrations/20261104_usage_days.sql` — one table, `usage_days`: one row
  a UTC day, how many people that day, in the 7 and the 30 days to it, how
  many accounts were counted and how many RevenueCat did not answer about,
  and the same day's and month's totals by place, app version and phone
  system. No account, no id, no address; the table refuses a breakdown that
  is not labels and whole numbers (`usage_breakdown_ok`). Row level
  security on, no policy, nothing granted to anon or authenticated.
  `record_usage_day(d, counts)` keeps only today (UTC): a count made
  before 23:43 UTC (by hand) is a first look that the night's replaces,
  and between the night's two the later is kept when it saw more people or
  RevenueCat missed no more of them. `owner_usage_days(most)` reads the
  days back; `usage_day_hook_secret()` and `run_usage_day()` are the
  nightly call. All service_role only. An app version is kept only as a
  version number (anything else is counted as Other). `run_usage_day()`
  deletes the days over two years old first, at every firing, before it
  asks for anything, so the privacy page's "kept two years, then deleted"
  holds even on a night the count fails. **If the `usage-days` job is ever
  taken off the schedule, empty or drop `public.usage_days` in the same
  change**, or nothing deletes the old days and the privacy page stops
  being true.
- `migrations/20261104_usage_days_schedule.sql` — the job alone, twice a
  night, 23:43 and 23:53 UTC (4:43 and 4:53 pm Mountain time in winter).
- `functions/grant-access/` — a third caller beside Justin and the
  entitlement function: a request carrying `x-hook-secret` is checked
  against `usage_day_hook_secret()`, in full, before any token is read, and
  may ask `usage-day` and nothing else. It counts exactly what People counts
  and hands the totals to `record_usage_day`. `usage` (People) also answers
  the last 31 days as `days` (null until the table exists, so People still
  works; a passing error reading them is `daysError`, which the page words
  as "couldn't be read just now", not as a missing change) and
  `unanswered`. `verify_jwt` stays on: the database sends the
  project's public key to get past the gateway, and the function's own lock
  is what keeps everybody else out.
- `functions/_shared/usage-count.mjs` — the counting rule itself, a copy of
  `shared/usage-count.mjs` made by `npm run sync:rules` (never edited by
  hand). grant-access imports it as `../_shared/usage-count.mjs`, so
  deploying grant-access sends three files: `grant-access/index.ts`,
  `_shared/forget-account.ts` and `_shared/usage-count.mjs`.
  `supabase functions deploy grant-access` bundles all three; any other
  way, send each at its path beside the function, or it will not start.

## Reading the reports without the full-account key (8 November 2026)

"A read-only login for bug reports ... so I can open people's reports
myself instead of you forwarding the emails" (Justin said yes, 8 November
2026). `scripts/report.mjs` read `public.feedback` through the Management
API with the full-account `SUPABASE_TOKEN`, which can do anything at all to
the project. Now it asks a function that answers two questions and nothing
else, to a caller holding a key that can do nothing else. Three pieces:

- `migrations/20261108_report_readers.sql` — `private.report_reader_keys`,
  the SHA-256 of each key (never the key), at most three, in a schema the
  API does not serve, with row level security on, no policy and nothing
  granted to anon or authenticated. Four database functions, service_role
  only: `report_reader_hashes()` and `enroll_report_reader(key_hash,
  replace_others)` for the keys, and the two questions the script used to
  send as SQL, fixed here word for word, `read_reports_latest(most)` (1 to
  50) and `read_report(prefix)` (8 to 36 hex digits and dashes, the newest
  two that start so).
- `functions/read-reports/` — `GET ?latest=N` and `GET ?id=<prefix>`,
  answered only to a request whose `x-reports-key` header hashes to a kept
  one (every kept hash compared in constant time; 401 otherwise, before
  anything else is looked at), and `POST /enroll`, shut unless the function
  secret `READ_REPORTS_ENROLL` is set. Nothing else: no way to write,
  change or delete a report, and no other table. No CORS, so no web page
  can read an answer. The key is never logged, never answered, and never
  sent on to the database (only its hash is).
- `scripts/report.mjs` — the same command line and the same output, asking
  the function. It sends no key itself: the session's network proxy adds
  `x-reports-key` to every request to the project's host, from the
  credential Justin saves in its secure form. Off the proxy,
  `READ_REPORTS_KEY` is the key, given to curl on stdin. The old way is
  still there for the day the function is down, off unless asked:
  `--management-api`, with `SUPABASE_TOKEN`.

Every session in the environment that holds the credential sends the key
to every address on `biznwrqeckviawjuhvyg.supabase.co`, the other
functions included. None of them logs a request's headers, and
test/read-reports.mjs fails if one starts to. Keep that environment
personal: one shared with the organization would hand the key to other
people's sessions too.

### Putting it live, in this order

1. **Apply `20261108_report_readers.sql`.** Nothing anybody sees changes.
2. **Merge the change, with every check green.** No What's new line (it is
   internal) and no build: nothing in the app moves. From here
   `node scripts/report.mjs` asks the function, so until step 5 it says the
   key was refused; `--management-api` reads the old way meanwhile.
3. **Deploy read-reports from the merged commit's files, with verify JWT
   off**: `supabase functions deploy read-reports --no-verify-jwt
   --project-ref biznwrqeckviawjuhvyg` (with no CLI installed,
   `npx supabase` with `--use-api`), or the Supabase connector's
   `deploy_edge_function` with `verify_jwt: false` and the one file,
   `index.ts`. With verify JWT on, the gateway refuses every call before
   the function sees it, because the caller has no Supabase sign-in.
4. **Justin saves the key, in the secure form, never in the chat.** The
   lead asks for it with the credential form: host
   `biznwrqeckviawjuhvyg.supabase.co`, header `x-reports-key`, no word
   before the value, named "Bug reports key". Justin makes up a long
   password (20 to 256 ordinary characters; a phrase of five or six words
   is fine) and types it there. He never needs it again: nobody reads it
   back, and a forgotten one is simply replaced (below). This can happen
   any time before step 5.
5. **Enrol the key, in one shell command**, so the one-time token is made
   in the shell, goes nowhere but the two requests (always on curl's stdin,
   never on a command line), and is gone when the subshell ends. It opens
   enrolment, enrols the key the proxy adds to the request (the command
   sends no key of its own), and shuts enrolment again whatever happened
   (the trap). It prints a few short lines and never the token:

   ```sh
   (
     set -eu
     API=https://api.supabase.com/v1/projects/biznwrqeckviawjuhvyg/secrets
     FN=https://biznwrqeckviawjuhvyg.supabase.co/functions/v1/read-reports
     auth() { printf 'Authorization: Bearer %s\n' "$SUPABASE_TOKEN"; }
     shut() { printf '["READ_REPORTS_ENROLL"]' | curl -sS -o /dev/null -w 'shut: %{http_code}\n' -X DELETE "$API" -H @<(auth) -H 'Content-Type: application/json' --data-binary @-; }
     T=$(openssl rand -hex 32)
     trap shut EXIT
     printf '[{"name":"READ_REPORTS_ENROLL","value":"%s"}]' "$T" | curl -sS --fail-with-body -o /dev/null -w 'open: %{http_code}\n' -X POST "$API" -H @<(auth) -H 'Content-Type: application/json' --data-binary @-
     printf '{"enroll":"%s"}' "$T" | curl -sS --fail-with-body --retry 6 --retry-delay 5 --retry-all-errors -X POST "$FN/enroll" -H 'Content-Type: application/json' --data-binary @-
     echo
   )
   ```

   `open: 201` (or 200), then the function's answer,
   `{"ok":true,"why":"enrolled","keys":1}`, then `shut: 200`. Before the
   answer there may be a refusal or two, `curl: (22) ... 403` with
   `enrolment is closed`: a new secret can take a few seconds to reach the
   function, and curl asks again every 5 seconds, seven times in all. Other
   answers: `no x-reports-key ...` (400) means the proxy sent no key, so
   step 4 is not done or the credential's host or header is not exactly as
   above; `three keys are kept already` (409), see below. If `shut:` says
   anything but 200, run the block's `API=`, `auth()` and `shut()` lines
   again in a shell, then `shut`: enrolment must not stay open.

### Changing the key, or taking it back

- **To change it** (forgotten, or shown somewhere it should not have been):
  Justin changes the "Bug reports key" credential's value in the
  environment's settings (or deletes it, and the lead asks for it again
  with the form, as in step 4). Then the lead runs step 5's command with
  `"replace":true` in the enrolment body, `printf
  '{"enroll":"%s","replace":true}' "$T"`, which keeps the new key and
  takes back every other in one step.
- **To take every key back at once**, the lead runs, as the project's own
  SQL (the SQL editor, or the connector's `execute_sql`):
  `delete from private.report_reader_keys where true;`. Every read is a 401
  from that moment. Justin also deletes the credential from the
  environment's settings, so the proxy stops sending it.
- **To take back one of several**: find it by the day it was enrolled
  (`select left(hash, 12), created_at ...`, as in Checking it, step 4),
  then `delete from private.report_reader_keys where hash like
  '<those 12>%';`.
- **The cap**: three keys at most, so enrolment answers 409 when three are
  kept; replace, or take one back first.
